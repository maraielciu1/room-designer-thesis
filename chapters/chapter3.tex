\chapter{3D Gaussian Splatting}
\label{ch:theory2}

Neural radiance fields (NeRF) showed that a scene can be encoded as a continuous volumetric function approximated by a neural network, enabling high-quality view synthesis from posed images. Training and rendering were initially slow. \textbf{3D Gaussian Splatting} (3DGS), introduced by Kerbl et al.\ \cite{kerbl20233dgs}, replaces the neural field by a set of \textbf{explicit anisotropic Gaussians} in space. Kerbl et al.\ show that this representation delivers \textbf{high visual quality together with real-time rendering}: their method matches or exceeds prior radiance-field quality while running at interactive frame rates on desktop GPUs \cite{kerbl20233dgs}. In this thesis, 3DGS is used as an \textbf{imported} representation (\texttt{.ply} files) rendered with a custom Metal pipeline for \textbf{comparison and viewing}; mesh-based USDZ assets remain the medium for interactive furniture editing. Figure~\ref{fig:ch3_nerf_pipeline} illustrates the NeRF rendering formulation that motivated later explicit real-time representations such as 3D Gaussian Splatting.

\section{Representation: 3D Gaussian Primitives}
\label{sec:3dgs_representation}

Each primitive stores a mean $\boldsymbol{\mu} \in \mathbb{R}^3$, a covariance $\boldsymbol{\Sigma}$ describing elongation and orientation, an opacity $\alpha$, and colour parameters. Following Kerbl et al.\ \cite{kerbl20233dgs}, $\boldsymbol{\Sigma}$ is built from a rotation matrix $\mathbf{R}$ (quaternion $\mathbf{q}$) and diagonal scale $\mathbf{S}=\operatorname{diag}(\mathbf{s})$ with positive entries: $\boldsymbol{\Sigma} = \mathbf{R}\mathbf{S}\mathbf{S}^\top\mathbf{R}^\top$. Colour may be view-dependent via spherical harmonics; the implementation described later also accepts per-Gaussian RGB in linear space.

The spatial falloff is
\[
G(\mathbf{x}) = \exp\bigl(-\tfrac{1}{2}(\mathbf{x}-\boldsymbol{\mu})^\top \boldsymbol{\Sigma}^{-1} (\mathbf{x}-\boldsymbol{\mu})\bigr).
\]

\centering
\thesisfig{\textwidth}{figures/fig3_2_gaussian_splatting_projection.pdf}
\caption{Conceptual illustration of 3D Gaussian projection and 
splatting. Each 3D Gaussian primitive with mean $\boldsymbol{\mu}$ 
and covariance $\Sigma$ is projected onto the image plane via the 
Jacobian $J$ of the perspective mapping, yielding an oriented 
elliptical footprint with 2D covariance $\Sigma'$. Footprints are 
sorted by depth and composited per pixel using alpha blending: 
$c_{\mathrm{out}} = \alpha \cdot c_G + (1-\alpha)\cdot 
c_{\mathrm{in}}$, where $c_G$ is the view-dependent colour of the 
Gaussian primitive, $\alpha$ is its opacity, and $c_{\mathrm{in}}$ 
is the accumulated colour from primitives behind it  \cite{kerbl20233dgs}.}
\label{fig:gaussian_project}
\end{figure}

\section{Projection, Rasterisation, and Real-Time Rendering}
\label{sec:3dgs_splatting}

Rendering splats each Gaussian onto the image \cite{kerbl20233dgs}:

\begin{enumerate}
    \item \textbf{Project} $\boldsymbol{\mu}$ with the camera matrix.

    \item \textbf{Project covariance} to $2\times2$ image-space covariance using the Jacobian $\mathbf{J}$ of the perspective mapping at $\boldsymbol{\mu}$, yielding an elliptical footprint.

    \item \textbf{Sort} primitives (globally or per tile) for approximate depth order.

    \item \textbf{Rasterise} with alpha blending, accumulating colour and transmittance along rays.
\end{enumerate}

Kerbl et al.\ describe tile-based culling and sorting strategies that make the above pipeline practical for \textbf{real-time} use \cite{kerbl20233dgs}. At each pixel, ordered compositing follows the familiar over-operator,
\[
\mathbf{c}_{\mathrm{out}} = \alpha \cdot \mathbf{c}_{\mathrm{G}} + (1-\alpha) \mathbf{c}_{\mathrm{in}}.
\]

\section{Differentiable Rendering and Optimisation}
\label{sec:3dgs_differentiable}

To fit Gaussians to photographs, the renderer must be \textbf{differentiable}. Gradients of a photometric loss $\mathcal{L}$ with respect to rendered pixels propagate backwards through:

\begin{enumerate}
    \item \textbf{Alpha compositing}: partial derivatives adjust per-Gaussian colour and opacity.

    \item \textbf{Rasterisation}: pixels influenced by a Gaussian receive scattered gradients.

    \item \textbf{Projection}: errors on the image plane differentiate through the projective transform and through the \textbf{Jacobian} $\mathbf{J}$ that maps 3D covariance to 2D, updating $\boldsymbol{\mu}$, scales, and rotations.
\end{enumerate}

This is structurally analogous to other differentiable rendering pipelines: screen-space residuals are tied to 3D parameters through a projection map. Optimisation typically alternates gradient steps with \textbf{adaptive density control} (splitting large Gaussians, culling transparent ones) \cite{kerbl20233dgs}. Initialisation often starts from a sparse point cloud (e.g.\ from COLMAP SfM), linking 3DGS training back to the same family of geometry estimation as Section~\ref{sec:photogrammetry}.

\subsection{Limitations of Classical 3DGS for Mobile and Real-Time Capture}
\label{subsec:3dgs_limitations}

Despite its visual quality and real-time rendering speed, the original 3DGS
pipeline~\cite{kerbl20233dgs} carries significant practical constraints that
limit its applicability in a mobile, user-facing scenario:

\begin{itemize}
    \item \textbf{Multi-view requirement.} Classical 3DGS requires a set of
    photographs taken from multiple, carefully distributed viewpoints around
    the subject,  typically 50-200+ images. This makes it unsuitable for
    capturing a scene from a single photo or from a handheld device with
    limited movement.

    \item \textbf{Dependency on SfM.} Before training can begin, camera
    poses must be estimated by running Structure-from-Motion (SfM) software
    such as COLMAP. This is a computationally
    expensive offline process (minutes to hours) and requires sufficient
    feature overlap between views.

    \item \textbf{Per-scene optimisation.} Each new scene requires running the
    full training loop from scratch, hundreds of thousands of gradient-descent
    iterations on a GPU. There is no generalisation across scenes: a model
    trained on one room cannot directly reconstruct another without retraining.

    \item \textbf{Adaptive densification overhead.} The original 3DGS algorithm
    dynamically splits and clones Gaussians in under-reconstructed regions and
    prunes near-transparent ones. While effective, this adaptive control makes
    training non-trivial to port to mobile hardware.

    \item \textbf{Relative scale.} Classical 3DGS initialises from a COLMAP
    sparse point cloud which provides only relative (up-to-similarity) scale.
    Without an explicit depth sensor or known camera baseline, the metric scale
    of the scene is unknown.
\end{itemize}

These constraints collectively make the classical pipeline impractical for
real-time, user-initiated mobile capture. The need for a \emph{generalised,
feedforward} approach that works from a single image motivated the development
of Apple's SHARP framework, described below.

\section{Meshes versus Gaussians: Editability and Role in the Application}
\label{sec:3dgs_vs_mesh}

\textbf{Meshes (USDZ from Object Capture)} are products of an on-device pipeline analogous to multi-view stereo plus \textbf{surface reconstruction} (e.g.\ Poisson reconstruction \cite{kazhdan2006poisson} in the classical photogrammetry literature). Such meshes expose \textbf{explicit connectivity}: faces can be clipped, simplified, or rigged; axis-aligned bounding boxes align naturally with RoomPlan's boxy furniture detections; RealityKit loads USDZ natively. \textbf{3D Gaussians} \cite{kerbl20233dgs} do not define a thin surface: ``moving'' an object means transforming thousands of primitives coherently; boolean cuts and physical simulation are ill-defined without conversion.

Therefore the product decision in this thesis is:

\begin{itemize}
    \item \textbf{Authoring and replacement}: USDZ meshes only.

    \item \textbf{Visualisation and comparison}: optional \texttt{.ply} splats via Metal, citing Kerbl et al.\ \cite{kerbl20233dgs} for the real-time splatting paradigm.

    \item \textbf{Training}: off-device in the current system; mobile or fast training remains future work \cite{Guo26}.
\end{itemize}

\section{Limitations of Classical 3DGS for Mobile and Real-Time Capture}
\label{sec:3dgs_limitations}

Despite its visual quality and real-time rendering speed, the 3DGS pipeline
of Kerbl et al.~\cite{kerbl20233dgs} carries practical constraints that limit its
applicability in a mobile, user-facing scenario:

\begin{itemize}
    \item \textbf{Multi-view requirement.} Classical 3DGS requires 50--200+
    photographs from distributed viewpoints. This makes it unsuitable for
    capturing a scene from a single photo or from a handheld device with
    limited movement.

    \item \textbf{Dependency on SfM.} Camera poses must be estimated by
    running Structure-from-Motion software such as COLMAP~\cite{SSF16} before
    training can begin (an offline process taking minutes to hours).

    \item \textbf{Per-scene optimisation.} Each new scene requires running the
    full training loop from scratch. There is no generalisation: a model
    trained on one room cannot reconstruct another without retraining.

    \item \textbf{Relative scale only.} Initialisation from a COLMAP sparse
    point cloud yields only relative scale. Without an explicit depth sensor
    or known baseline, metric scale is unknown.
\end{itemize}

These constraints make the classical pipeline impractical for real-time,
user-initiated mobile capture, motivating the feedforward approach described
below.

\section{SHARP: Feedforward Single-Image 3D Gaussian Splatting}
\label{sec:sharp}

\textbf{SHARP} (\emph{Sharp Monocular View Synthesis})~\cite{sharp-monocular-view} is a
method developed at Apple and presented at ICLR~2025. Given a \emph{single}
RGB photograph, SHARP predicts the full set of 3D Gaussian parameters for the
depicted scene in one forward pass through a neural network, with no
iterative optimisation, no multi-view input, and no SfM preprocessing. The
output is a standard \texttt{.ply} that renders in real time via the same
splatting pipeline. Inference takes
under one second on a modern GPU.

The method builds on a pretrained monocular depth estimator (Depth
Pro~\cite{BDGZ25}) to initialise $\approx$1.2 million Gaussians from the
predicted metric depth map, then refines all Gaussian attributes through a
learned decoder. This design yields three key properties: (1)~real-time
novel-view rendering via standard 3DGS rasterisation; (2)~absolute metric
scale, enabling physically meaningful camera displacements compatible with
AR/VR sensors; and (3)~zero-shot generalisation across indoor and outdoor
scenes, reducing LPIPS by 25--34\% and DISTS by 21--43\% versus the best
prior feedforward method on six benchmark datasets~\cite{sharp-monocular-view}.

\subsection{Integration in This Application}
\label{subsec:sharp_integration}

The application integrates SHARP as a supplementary capture mode alongside
RoomPlan and Object Capture, using a client--server architecture:

\begin{itemize}
    \item \textbf{Server (Python/PyTorch).} A Flask server
    (\texttt{sharp\_server.py}) runs on a Mac on the local network. It loads
    the pretrained SHARP weights once at startup and exposes a
    \texttt{/sharp/infer} endpoint. When a JPEG is posted, the server calls
    \texttt{predict\_image()}, applies opacity-based Gaussian pruning to
    reduce $\approx$1.2\,M to $\approx$300\,k Gaussians for mobile rendering
    performance, and returns the \texttt{.ply} file.

    \item \textbf{Client (SwiftUI/iOS).} \texttt{SHARPCaptureView} lets the
    user capture one frame via \texttt{UIImagePickerController}.
    \texttt{SHARPService.infer(image:)} POSTs the JPEG using a custom
    \texttt{URLSession} with a 360-second timeout (the default
    \texttt{URLSession.shared} caps at 60\,s, insufficient for first-run
    Metal shader compilation on the server), saves the returned \texttt{.ply},
    and opens it in the existing Metal orbit viewer.

    \item \textbf{Gaussian pruning.} The full SHARP output produces a
    $\approx$66\,MB \texttt{.ply}. The per-frame Metal depth-sort over 1.2\,M
    elements is too expensive for interactive rates on iPhone. The server
    therefore retains the top 300\,k Gaussians by opacity score, reducing the
    file to $\approx$18\,MB and enabling smooth real-time viewing on device.
\end{itemize}

This positions the application to demonstrate the full reconstruction
spectrum: \textbf{RoomPlan} (parametric, real-time) $\rightarrow$
\textbf{Object Capture} (photogrammetric mesh, on-device) $\rightarrow$
\textbf{3DGS} (optimisation-based, external GPU) $\rightarrow$
\textbf{SHARP} (feedforward neural, single image, near real-time).
